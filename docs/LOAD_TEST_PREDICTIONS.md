# 채팅 시스템 부하 테스트 예측치

## 📊 테스트 환경 기반 정보

### **현재 시스템 구성**

```yaml
Kubernetes 클러스터:
  - Pods: 3개
  - CPU per Pod:
    - Request: 200m (0.2 Core)
    - Limit: 1000m (1 Core)
  - Memory per Pod:
    - Request: 512Mi
    - Limit: 1Gi

총 리소스:
  - CPU: 600m request, 3000m limit (3 Cores)
  - Memory: 1.5Gi request, 3Gi limit

데이터베이스:
  - MySQL (Master/Slave 구성)
  - Connection Pool: 30 connections
  
네트워크:
  - WebSocket 기반 실시간 통신
  - Load Balancer: Kubernetes Service
```

---

## 🎯 예측 방법론

### **1. CPU 기반 처리량 계산**

```
기본 가정:
- 메시지 1개 처리 = 10ms CPU 시간
- 1 Core = 1000ms/s
- Pod당 실제 사용 가능: 800m (오버헤드 20%)

계산:
Pod 1개당 처리량 = 800ms / 10ms = 80 메시지/초
3 Pods = 240 메시지/초 (베이스라인)
```

### **2. 메모리 기반 동시 접속자 계산**

```
기본 가정:
- WebSocket 연결 1개 = 1MB 메모리
- Pod당 사용 가능 메모리: 800Mi (오버헤드 20%)

계산:
Pod 1개당 연결 = 800 연결
3 Pods = 2,400 연결 (안전 마진 20% 적용 시 → 2,000명)
```

### **3. Redis/Kafka 개선 효과 예측**

```
Redis Pub/Sub 도입 시:
- DB 쿼리 90% 감소 → CPU 부하 50% 감소
- 메시지 전달 시간 80% 단축
- 예상 개선: 3-4배

Kafka 도입 시:
- 비동기 처리로 CPU 효율 70% 향상
- 메시지 버퍼링으로 스파이크 흡수
- 예상 개선: 5-10배
```

## 📈 시나리오별 예측치

### **시나리오 1: 일반 채팅 (Baseline Test)**

**테스트 설정:**
- Virtual Users: 1,000명
- Duration: 10분
- 메시지 빈도: 5초당 1개 (0.2 메시지/초/인)

#### **예측 결과표**

| 지표 | Redis 전 | Redis 후 | Kafka 후 | 예측 근거 |
|------|----------|----------|----------|-----------|
| **총 TPS** | 400-500 | 1,600-2,000 | 8,000-10,000 | CPU 여유, DB 병목 해소 |
| **동시 접속자** | 1,500명 | 3,000명 | 10,000명 | 메모리 기반 계산 |
| **P50 응답 시간** | 80-100ms | 8-12ms | 5-8ms | DB 쿼리 → 메모리 캐시 |
| **P95 응답 시간** | 150-200ms | 18-25ms | 10-15ms | 꼬리 지연 감소 |
| **P99 응답 시간** | 300-400ms | 45-60ms | 20-30ms | 최악 케이스 개선 |
| **메시지 유실률** | 0.5-1.0% | 0.03-0.05% | 0.001-0.01% | 안정성 향상 |
| **에러율** | 2-4% | 0.5-1.0% | 0.1-0.3% | 타임아웃 감소 |
| **CPU 사용률** | 70-85% | 40-50% | 35-45% | DB 부하 감소 |
| **Memory 사용률** | 60-75% | 55-70% | 60-75% | Redis/Kafka 메모리 추가 |
| **DB Connection** | 22-28/30 | 5-10/30 | 3-7/30 | 쿼리 수 감소 |
| **Network I/O** | 30-40MB/s | 45-60MB/s | 70-90MB/s | Redis/Kafka 트래픽 |

#### **상세 예측**

```yaml
처리량 (TPS):
  Redis 전: 450 ± 50
    - 근거: DB 쓰기 병목, CPU 75% 사용 시점에서 한계
    - 계산: 1,000명 × 0.2 msg/s = 200 msg/s (이론)
            실제 DB 쓰기 지연으로 2.2배 증가 → 450 msg/s
  
  Redis 후: 1,800 ± 200
    - 근거: DB 쿼리 90% 감소, CPU 효율 3.5배 향상
    - 계산: 450 × 4 = 1,800 msg/s
  
  Kafka 후: 9,000 ± 1,000
    - 근거: 비동기 처리, 배치 처리, 확장성
    - 계산: 450 × 20 = 9,000 msg/s

응답 시간 (P95):
  Redis 전: 180ms
    - WebSocket 전송: 10ms
    - 서버 처리: 20ms
    - DB 쓰기: 100ms ← 병목
    - 브로드캐스트: 50ms
    
  Redis 후: 22ms
    - WebSocket 전송: 10ms
    - 서버 처리: 5ms
    - Redis Pub: 2ms
    - 브로드캐스트: 5ms
    
  Kafka 후: 13ms
    - WebSocket 전송: 10ms
    - Kafka Producer: 3ms (비동기)
    - 실제 사용자는 13ms만 대기

메시지 유실률:
  Redis 전: 0.8%
    - DB Timeout: 0.5%
    - Pod Crash: 0.2%
    - Network Error: 0.1%
    
  Redis 후: 0.05%
    - Pod Crash: 0.03%
    - Network Error: 0.02%
    
  Kafka 후: 0.005%
    - Kafka 영속성으로 거의 0에 수렴
```
