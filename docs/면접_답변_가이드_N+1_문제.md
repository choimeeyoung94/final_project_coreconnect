### **질문 1: "N+1 문제를 어떻게 발견했나요?"**

**답변 구조: 문제 발견 → 로그 분석 → 패턴 확인**

```
(1단계: 문제 발견)
"k6 부하 테스트 중 채팅방 목록 조회 API의 응답시간이 
예상(100ms)보다 50배 느린 5초를 기록했습니다.

(2단계: 로그 분석)
원인을 찾기 위해 application.yml에 
Hibernate SQL 로그와 Statistics를 활성화했습니다.

(3단계: 패턴 확인)
로그를 분석한 결과, 채팅방 10개를 조회할 때 
31개의 쿼리가 실행되는 것을 발견했습니다.

쿼리 패턴은 이렇습니다:
- 1개: 채팅방 목록 조회
- 10개: 각 채팅방의 최신 메시지 조회
- 10개: 각 메시지의 발신자 정보 조회 (Lazy Loading)
- 10개: 각 메시지의 채팅방 정보 조회 (Lazy Loading)
총 1 + 10×3 = 31개 쿼리입니다.

(4단계: 원인 규명)
Chat 엔티티의 sender와 chatRoom이 FetchType.LAZY로 설정되어,
DTO 변환 시 getName()을 호출할 때마다 
추가 SELECT 쿼리가 발행되는 전형적인 N+1 문제였습니다."
```

**핵심 포인트:**
- ✅ 정량적 수치 (6.3초, 31개 쿼리)
- ✅ 구체적 도구 (k6, Hibernate 로그)
- ✅ 패턴 분석 (1 + N×3)
- ✅ 원인 규명 (Lazy Loading)

### **질문 2: "왜 Fetch Join을 선택했나요? 다른 방법은?"**

**답변 구조: 비교 분석 → 선택 이유 → 트레이드오프**

```
(1단계: 비교 분석)
"5가지 해결 방법을 비교 분석했습니다:

1) Fetch Join: 쿼리 1개로 감소, JPQL로 명시적 제어
2) @EntityGraph: 코드 간결, 단 복잡한 서브쿼리와 제약
3) Batch Fetch Size: 쿼리 여전히 많음 (1 + 2개)
4) DTO 직접 조회: 메모리 효율적, 단 엔티티 사용 불가
5) FetchType.EAGER: 불필요한 조회 증가 (안티패턴)

(2단계: 선택 이유)
Fetch Join을 선택한 3가지 이유입니다:

첫째, 쿼리 수 최소화.
31개를 1개로 줄여 DB 왕복 시간을 97.6% 단축했습니다.

둘째, 명시적 제어.
JPQL에서 정확히 어떤 연관 관계를 로드할지 명시하고,
서브쿼리(MAX)와 함께 사용할 수 있습니다.

셋째, Left Join 지원.
시스템 메시지처럼 sender가 null인 경우에도
Left Join으로 조회 가능합니다.

(3단계: @EntityGraph와 차이)
@EntityGraph도 테스트했지만,
복잡한 서브쿼리와 함께 사용 시 
Hibernate가 추가 쿼리를 발행하는 문제가 있었습니다.

Fetch Join은 JPQL에서 자유롭게 
WHERE, ORDER BY와 조합할 수 있어 더 유연합니다.

(4단계: 트레이드오프)
단, Fetch Join의 단점도 있습니다:

1) Pagination 제약: 메모리에서 페이징 → OutOfMemoryError 위험
   → 우리 프로젝트는 채팅방 최대 100개로 제한해 문제 없음

2) Cartesian Product: 여러 OneToMany 동시 Fetch Join 시 데이터 중복
   → sender, chatRoom은 ManyToOne이라 문제 없음

3) 불필요한 컬럼 조회: 연관 엔티티의 모든 컬럼 조회
   → User, ChatRoom 컬럼 수가 10개 이하로 적고, 
      엔티티 재사용이 필요해 Fetch Join 유지"
```

**핵심 포인트:**
- ✅ 5가지 방법 비교 (폭넓은 지식)
- ✅ 선택 근거 3가지 (논리적 사고)
- ✅ @EntityGraph 테스트 (실험 정신)
- ✅ 트레이드오프 인식 (현실적 판단)

### **질문 3: "Fetch Join의 단점은 무엇인가요?"**

**답변 구조: 단점 3가지 → 해결 방법 → 우리 프로젝트 적용**

```
"Fetch Join의 3가지 주요 단점과 해결 방법입니다:

(단점 1: Pagination 제약)
문제: Fetch Join + Pagination 조합 시 
      Hibernate가 DB에서 모든 데이터를 가져온 후 
      메모리에서 페이징합니다.
      데이터 10만 건이면 OutOfMemoryError 위험이 있습니다.

해결: ID만 먼저 페이징 조회 후 Fetch Join으로 상세 조회.
      또는 Batch Fetch Size 설정으로 IN 절 사용.

우리 프로젝트: 채팅방 최대 100개로 제한해 문제 없습니다.

(단점 2: Cartesian Product)
문제: 여러 OneToMany 관계를 동시에 Fetch Join하면
      데이터 중복이 발생합니다.
      예: Chat 1개 + messageFiles 3개 + reactions 5개
          → 1 × 3 × 5 = 15개 행 반환 (중복!)

해결: ManyToOne만 Fetch Join, OneToMany는 별도 쿼리 분리.
      또는 @EntityGraph + DISTINCT 사용.

우리 프로젝트: sender, chatRoom은 ManyToOne이라 
              Cartesian Product가 발생하지 않습니다.

(단점 3: 불필요한 컬럼 조회)
문제: Fetch Join은 연관 엔티티의 모든 컬럼을 조회합니다.
      user 테이블에 50개 컬럼이 있어도 
      필요한 건 name 하나뿐인 경우 비효율적입니다.

해결: DTO 직접 조회 (new JPQL 구문)로 필요한 컬럼만 SELECT.

우리 프로젝트: User, ChatRoom 컬럼 수가 10개 이하로 적고,
              DTO 변환 후에도 엔티티 메서드를 사용해야 해서
              Fetch Join을 유지했습니다."
```

**핵심 포인트:**
- ✅ 단점 3가지 (정확한 이해)
- ✅ 각 단점의 해결 방법 (문제 해결 능력)
- ✅ 우리 프로젝트 상황 (현실 적용)
- ✅ 트레이드오프 판단 (시니어 마인드)

### **질문 5: "인덱스는 어떻게 설계했나요?"**

**답변 구조: 설계 원칙 → 검증 → 무중단 배포**

```
"복합 인덱스 설계 시 3가지 원칙을 적용했습니다:

(원칙 1: 카디널리티 순서)
카디널리티가 높은 컬럼을 먼저 배치했습니다.

(chat_room_id, sent_at) 순서로 설계한 이유:
- WHERE chat_room_id = ? (카디널리티 높음, 선택도 높음)
- ORDER BY sent_at DESC (카디널리티 중간, 정렬 필요)

(원칙 2: Covering Index)
쿼리에 필요한 모든 컬럼을 인덱스에 포함했습니다.
MySQL EXPLAIN 결과 'Extra: Using index'로
인덱스만으로 조회가 완료됩니다.

(원칙 3: MySQL EXPLAIN 검증)
인덱스 생성 전후를 EXPLAIN으로 검증했습니다:

Before:
- type: ALL (Full Table Scan)
- rows: 100,000

After:
- type: ref (Index Range Scan)
- rows: 2 (99.998% 감소)

(무중단 배포)
Online DDL을 사용해 무중단으로 인덱스를 생성했습니다:

CREATE INDEX idx_chat_room_sent_at
ON chat_message (chat_room_id, sent_at DESC)
ALGORITHM=INPLACE, LOCK=NONE;

서비스 다운타임 없이 인덱스를 추가할 수 있었습니다."
```

**핵심 포인트:**
- ✅ 설계 원칙 3가지 (체계적 사고)
- ✅ EXPLAIN 검증 (데이터 기반 판단)
- ✅ 무중단 배포 (실무 고려)

## 📌 면접 전날 반드시 암기할 3가지

### **1. 쿼리 수 계산식**
```
1 (채팅방 목록) + N×3 (메시지 + 발신자 + 채팅방) = 31개
→ Fetch Join으로 1개로 감소 (90.3% 개선)
```

### **2. 핵심 수치**
```
P95 응답시간: 6,300ms → 400ms (93.6% 개선)
처리량: 5.3 → 15 req/s (183% 증가)
Connection Pool: 100% → 37.5% (62.5% 감소)
```

### **3. 트레이드오프**
```
단점 1: Pagination 제약 → 우리는 100개 제한
단점 2: Cartesian Product → ManyToOne이라 문제 없음
단점 3: 불필요한 컬럼 → 10개 이하로 적음
```
