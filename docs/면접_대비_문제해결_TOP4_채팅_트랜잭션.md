# 면접 대비용 문제해결 문서 (채팅/트랜잭션 TOP4)

이 문서는 CoreConnect 프로젝트의 **문제-해결-성과**를 면접에서 **짧고 근거 있게** 설명하기 위한 정리 자료다.  
각 항목은 **질문 → 요약 답변 → 근거 포인트 → 꼬리 질문 대비** 순서로 구성했다.

---

## 1) WebSocket 실시간 채팅 지연/재연결 문제

### 질문
실시간 채팅에서 메시지 지연과 재연결 문제가 있었다고 했는데, 원인과 해결 과정을 설명해주세요.

### 요약 답변 (30~40초)
초기에 WebSocket 메시지 전송이 5–10초 지연되고 재연결이 빈번했습니다.  
Nginx WebSocket 프록시 설정이 기본값이라 업그레이드/타임아웃 처리와 버퍼링에 문제가 있었고,  
동시 접속 세션 관리도 안전하지 않아 연결이 자주 끊겼습니다.  
Nginx 프록시를 WebSocket에 맞게 최적화하고, 서버 측에서 사용자별 세션을 스레드 안전하게 관리하도록 개선해  
지연을 0.1초 수준으로 줄이고 재연결을 98.5% 감소시켰습니다.

### 근거 포인트 (면접에서 언급 가능한 키워드)
- Nginx WebSocket 프록시 최적화(업그레이드 헤더 처리, 버퍼/타임아웃 튜닝)
- 사용자별 동시 접속 세션 관리(스레드 안전 구조)
- 사용자 불만 건수 감소(주간 35건 → 0건)

### 꼬리 질문 대비
- **Q. 세션 관리는 어떻게 개선했나요?**  
  A. 사용자 ID 기준으로 세션을 관리하고, 동시 접속 환경에서 안전하도록 동시성 컬렉션을 사용했습니다.
- **Q. 왜 HTTP가 아닌 WebSocket인가요?**  
  A. 지속 연결로 지연을 줄이고 서버 부하를 낮추기 위해서입니다.

## 2) 메시지 읽음 처리 동시성 충돌

### 질문
읽음 처리에서 동시성 문제가 있었다고 했는데, 어떤 문제가 발생했고 어떻게 해결했나요?

### 요약 답변 (30~40초)
여러 디바이스/탭에서 동시에 읽음 처리 요청이 들어오면서  
읽음 카운트가 음수로 떨어지거나 불일치하는 문제가 있었습니다.  
읽음 업데이트 로직을 **단일 트랜잭션**으로 묶어 원자성을 보장했고,  
이벤트성 후처리는 `Propagation.REQUIRES_NEW`로 분리해 본 트랜잭션과 독립적으로 처리했습니다.  
그 결과 읽음 수 불일치가 0건으로 개선됐고 재처리/롤백 이슈가 사라졌습니다.

### 근거 포인트
- 단일 트랜잭션으로 읽음 처리 원자성 확보
- `Propagation.REQUIRES_NEW`로 이벤트성 후처리 분리
- 읽음 카운트 불일치 0건

### 꼬리 질문 대비
- **Q. 왜 `REQUIRES_NEW`가 필요했나요?**  
  A. 읽음 처리 자체는 반드시 성공/실패를 명확히 해야 하고, 부가 이벤트는 실패해도 본 트랜잭션에 영향 없도록 분리했습니다.
- **Q. DB 락이나 성능 문제는 없었나요?**  
  A. 핵심 업데이트 범위를 최소화했고, 이벤트 처리는 분리해 트랜잭션 시간을 줄였습니다.

## 3) 읽음 처리 이벤트 폭주 시 DB 락 경합

### 질문
대량 읽음 이벤트가 들어올 때 DB 락이 걸렸다는 내용이 있는데, 어떻게 완화했나요?

### 요약 답변 (30~40초)
읽음 이벤트가 폭주할 때 동일한 레코드를 동시에 갱신하면서 DB 락 경합이 심해졌습니다.  
즉시 처리 방식을 **비동기/배치화**로 전환해 트래픽을 분산했고,  
핵심 업데이트는 최소 범위로 유지해 락 대기를 줄였습니다.  
결과적으로 락 대기가 감소했고 읽음 반영 지연도 완화되었습니다.

### 근거 포인트
- 이벤트 처리 비동기/배치화로 부하 분산
- 락 대기 감소, 읽음 반영 지연 감소

### 꼬리 질문 대비
- **Q. 즉시 일관성이 깨지지 않나요?**  
  A. 읽음은 약간의 지연 허용이 가능해 최종 일관성 전략으로 설계했습니다.
- **Q. 배치 기준은 어떻게 잡았나요?**  
  A. 이벤트 수와 DB 부하를 기준으로 처리 주기를 조정했습니다.

## 4) 메시지 저장 + 알림 전송 간 정합성

### 질문
메시지 저장 실패인데 알림이 먼저 전송되는 문제가 있었다고 했는데, 어떻게 개선했나요?

### 요약 답변 (30~40초)
초기에는 메시지 저장과 알림 발송이 동시에 진행되어  
저장 실패인데 알림이 나가는 “유령 알림” 문제가 있었습니다.  
메시지 저장이 **트랜잭션으로 성공**한 뒤에만 도메인 이벤트를 발행하고,  
알림은 비동기로 처리하도록 변경해 순서를 보장했습니다.  
그 결과 유령 알림이 0건이 되었고 메시지-알림 정합성이 확보됐습니다.

### 근거 포인트
- 메시지 저장 트랜잭션 성공 후 이벤트 발행
- 알림 비동기 처리
- 유령 알림 0건

### 꼬리 질문 대비
- **Q. 왜 동기 발송을 하지 않았나요?**  
  A. 알림은 부가 기능이라 실패 시 재시도 가능하게 비동기로 처리하는 게 안정적입니다.
- **Q. 이벤트는 어디에서 발행했나요?**  
  A. 저장 성공 후 서비스 레이어에서 도메인 이벤트를 발행했습니다.
