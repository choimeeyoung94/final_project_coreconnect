## 옵션 A(클러스터 내부 Job) 마지막 테스트 분석 — 병목 지점 & 보완 방향

### 1) 테스트 요약(이번 결과의 의미)
- **테스트 방식**: k6를 **클러스터 내부 Job**으로 실행 → `chat-service`(ClusterIP)로 접속(분산 환경 재현)
- **관측 결과(요약)**:
  - 로그인/HTTP 실패율: **0%**
  - HTTP 지연: **P95 약 243ms**
  - WebSocket 연결 지연: (대시보드 상) **낮은 수준**

**결론**: 이번 수치는 “서버가 터지는 병목(CPU/메모리/DB 커넥션 고갈)”이 발생한 상태가 아니라,  
**아직 ‘한계치’까지 도달하지 않은 정상 구간**의 결과로 보는 게 맞습니다.  
따라서 “병목이 어디다”를 확정하려면 다음 회차에서 지표를 더 붙여 측정해야 합니다.

---

### 2) 지금 단계에서 가장 유력한 병목/한계 후보 2가지

#### (A) 아키텍처 한계: 멀티 Pod 팬아웃(전달 정합성)
- 공유 브로커(예: Redis Pub/Sub/RabbitMQ STOMP relay) 없이 `enableSimpleBroker("/topic")`를 사용하면,
  **브로드캐스트가 Pod(프로세스) 로컬**에 머물 수 있어 멀티 Pod에서 “방 전체 수신” 품질이 흔들릴 수 있습니다.
- 이 경우 Pod 수를 늘려도, **성능이 아니라 구조적 이유로 “전달률/정합성”이 먼저 깨질 수 있음**.

**보완(우선순위)**:
- **Redis Pub/Sub** 또는 **RabbitMQ STOMP relay**로 `/topic` 브로커를 외부로 분리해 Pod 간 팬아웃을 보장
- 그 다음에 “Pod 늘리면 동시 인원도 확장”이 성립

#### (B) DB 병목: 메시지 1건당 DB 작업량(쿼리/업데이트)이 과함
- 메시지 처리 흐름에서 “저장 + unreadCount 계산/갱신 + 참여자/접속자 조회” 등 DB 접근이 많으면,
  동시 송신이 올라갈수록 **MySQL 쿼리/락/커넥션**이 먼저 한계가 될 가능성이 큽니다.

**보완(우선순위)**:
- **unreadCount를 ‘메시지마다 DB count’로 재계산하지 않기**
  - Redis 캐시, 이벤트 기반 집계, 배치 처리 등으로 전환
- **필수 인덱스 적용**
  - read-status / chat-room-user / chat created_at 등(이미 문서에 제안된 인덱스부터)
- **flush/save 남발 최소화**
  - `saveAndFlush()`, `flush()` 반복은 TPS를 빠르게 깎는 요소
- **로그 레벨/로그량 제어**
  - 메시지/웹소켓 처리 INFO 로그 과다 시 I/O가 병목이 될 수 있음

### 3) “몇 명까지 견디나”를 의미 있게 만들기 위한 전제
채팅 부하는 “보내는 사람 수”보다 **팬아웃(받는 사람 수)**에 의해 폭발합니다.  
따라서 “최대 몇 명”은 아래를 함께 정의해야 숫자가 의미가 있습니다.
- **동시 접속자 수**
- **방당 평균 인원(=팬아웃 크기)**
- **메시지 빈도(msg/user/sec)**
- **성공 기준**(예: 에러율 < 1%, P95 < X ms, 채팅 메시지 수신률 ≥ 95% 등)

---

### 4) 다음 회차 측정(병목 확정) 체크리스트
이번은 “정상 구간”이므로, 다음에는 부하를 올리면서 아래 지표를 동시에 봐야 병목이 확정됩니다.

- **Pod 리소스**
  - `kubectl top pod -n chat-system`
- **DB**
  - 커넥션 수, slow query, lock wait, p95 쿼리 시간
- **서버 내부(가능하면)**
  - Hikari active/max, 스레드풀, WebSocket 세션 수

---

### 5) 권장 실행 플랜(단계별)
- **1단계(정합성 확보)**: Redis Pub/Sub(or RabbitMQ relay)로 멀티 Pod에서도 “방 전체 수신”이 되도록 구조 보완
- **2단계(계측 강화)**: 위 체크리스트로 병목 지표를 수집(로그/메트릭/DB)
- **3단계(부하 시나리오 강화)**:
  - `ROOM_COUNT=1` (최악 팬아웃) / `ROOM_COUNT=3~10` (현실 분산) 케이스를 분리 측정
  - `MESSAGES_PER_USER`를 3~5로 올려 메시지 처리량을 실제에 가깝게
  - 성공 기준(지연/에러/수신률)을 고정하고 최대 VU를 탐색
