## 4. 테스트 방법 이해

### 질문 3
**사용자**: 그럼 내가 테스트해야하는것은 k6를 우분투에 설치하고 각 api를 입력해서 테스트 하면 되는거야?

### 답변
**중요한 오해 해소**:

각 API를 수동으로 입력할 필요 없음! 테스트 스크립트가 자동으로 모든 API를 테스트함.

#### 실제로 해야 하는 것:

**1단계: k6 설치 (우분투)**
```bash
sudo gpg -k
sudo gpg --no-default-keyring --keyring /usr/share/keyrings/k6-archive-keyring.gpg --keyserver hkp://keyserver.ubuntu.com:80 --recv-keys C5AD17C747E3415A3642D57D77C6C491D6AC1D69
echo "deb [signed-by=/usr/share/keyrings/k6-archive-keyring.gpg] https://dl.k6.io/deb stable main" | sudo tee /etc/apt/sources.list.d/k6.list
sudo apt-get update
sudo apt-get install k6
k6 version
```

**2단계: 테스트 계정 준비**
- DB에 테스트용 사용자 계정 5개 이상 생성

**3단계: config.js 수정**
- TEST_USERS 배열을 실제 계정 정보로 변경

**4단계: 테스트 실행 (자동!)**
```bash
cd performance-tests

# 채팅 기능 테스트 - 자동으로 모든 채팅 API 호출
k6 run chat-test.js

# 알림 기능 테스트 - 자동으로 모든 알림 API 호출
k6 run notification-test.js

# 이메일 기능 테스트 - 자동으로 모든 이메일 API 호출
k6 run email-test.js

# 또는 전체 테스트 한 번에
./run-all-tests.sh
```

#### 자동으로 테스트되는 것들

**`k6 run chat-test.js` 실행 시 자동으로**:
- ✅ POST /api/v1/user/login (로그인)
- ✅ POST /api/v1/chat (채팅방 생성)
- ✅ POST /api/v1/chat/rooms/{roomId}/messages (메시지 전송)
- ✅ GET /api/v1/chat/{roomId}/messages (메시지 조회)
- ✅ GET /api/v1/chat/rooms/{roomId}/messages/unread-count (미읽은 개수)
- ✅ WebSocket /ws/chat (실시간 메시지)

**5명의 가상 사용자가 1분간 반복 테스트**

## 6. 데이터 보존 관련 질문

### 질문 7
**사용자**: 근데 지금 application.properties에 spring.jpa.hibernate.ddl-auto가 update로 되있어서 배포를 다시 하거나 하면 기존에 저장되 있던 사용자 데이터들이 전부 초기화 되는것 아니야?

### 답변

**중요한 오해 해소**:

`update` 설정은 데이터를 초기화하지 **않습니다**!

#### Hibernate ddl-auto 설정 비교

| 설정 | 동작 | 데이터 보존 |
|------|------|-----------|
| **create** | 기존 테이블 DROP 후 재생성 | ❌ 삭제됨 |
| **create-drop** | 시작 시 생성, 종료 시 DROP | ❌ 삭제됨 |
| **update** | 스키마 변경사항만 반영 (ALTER TABLE) | ✅ **유지됨** |
| **validate** | 스키마 검증만, 변경 안함 | ✅ 유지됨 |
| **none** | 아무것도 안함 | ✅ 유지됨 |

#### update의 동작 방식

```
배포 전: user 테이블에 6명의 사용자 데이터 존재
   ↓
재배포 (update 설정)
   ↓
1. 기존 테이블 구조 확인
2. 엔티티와 비교해서 변경사항 있으면 ALTER TABLE 실행
   (예: 새 컬럼 추가, 컬럼 타입 변경)
3. 기존 데이터는 그대로 유지
   ↓
배포 후: user 테이블에 6명의 사용자 데이터 그대로 존재 ✅
```

#### 실제 예시

```java
// 배포 전 엔티티
@Entity
public class User {
    @Id
    private Long id;
    private String email;
    private String password;
}

// 재배포 시 새 필드 추가
@Entity
public class User {
    @Id
    private Long id;
    private String email;
    private String password;
    private String phoneNumber;  // 새로 추가
}

// update 설정이면:
// → ALTER TABLE user ADD COLUMN phone_number VARCHAR(255);
// → 기존 데이터는 유지, phone_number만 NULL로 추가됨
```

#### 데이터가 삭제되는 경우

오직 이 경우들만:
1. ❌ `ddl-auto=create` 또는 `create-drop`으로 설정
2. ❌ 수동으로 `DROP TABLE` 실행
3. ❌ 데이터베이스 전체 삭제

#### 운영 환경 권장 설정

```properties
# 개발/테스트 환경
spring.jpa.hibernate.ddl-auto=update  # 현재 설정 (괜찮음)

# 운영 환경 (권장)
spring.jpa.hibernate.ddl-auto=validate  # 검증만
# 또는
spring.jpa.hibernate.ddl-auto=none  # 아무것도 안함
# 스키마 변경은 Flyway/Liquibase 같은 마이그레이션 도구 사용
```

#### 테스트 계정을 더 안전하게 관리하는 방법

**data.sql 파일 생성** (`src/main/resources/data.sql`):

```sql
-- 테스트 계정이 없으면 자동으로 생성
INSERT INTO user (email, password, name, department, role)
SELECT 'admin@coreconnect.io.kr', '$2a$10$...', '관리자', '대표', '관리자'
WHERE NOT EXISTS (SELECT 1 FROM user WHERE email = 'admin@coreconnect.io.kr');

INSERT INTO user (email, password, name, department, role)
SELECT 'kms@coreconnect.io.kr', '$2a$10$...', '김민석', '자장', '일반'
WHERE NOT EXISTS (SELECT 1 FROM user WHERE email = 'kms@coreconnect.io.kr');

-- ... 나머지 계정들
```

**application.properties 설정**:

```properties
spring.jpa.hibernate.ddl-auto=update
spring.sql.init.mode=always  # data.sql 항상 실행
```

이렇게 하면 배포할 때마다 테스트 계정이 자동으로 생성됩니다 (이미 있으면 건너뜀).

#### 결론

✅ **현재 `update` 설정으로는 데이터가 초기화되지 않습니다.**
✅ **배포를 여러 번 해도 사용자 데이터는 그대로 유지됩니다.**
✅ **바로 k6 테스트를 진행하셔도 됩니다!**

## 📚 주요 학습 내용

### 1. k6 테스트는 자동화됨
- ❌ API를 수동으로 하나씩 호출하는 것이 아님
- ✅ 스크립트 실행 하나로 모든 API를 자동 테스트

### 2. 테스트 계정 설정
- config.js의 TEST_USERS에 실제 계정 정보 입력
- 비밀번호는 DB 해시값이 아닌 원본 비밀번호 사용
- 로그인 API를 통해 JWT 토큰 자동 획득

### 3. Hibernate ddl-auto 설정
- `update`: 스키마 변경만, 데이터 유지 ✅
- `create`: 테이블 재생성, 데이터 삭제 ❌
- `validate`: 검증만, 변경 없음 ✅ (운영 환경 권장)

### 4. 성능 테스트 흐름
```
1. 스모크 테스트 (빠른 검증)
   ↓
2. 부하 테스트 (성능 측정)
   ↓
3. 결과 분석 (병목 지점 파악)
   ↓
4. 성능 개선 (인덱스, 캐싱, 비동기)
   ↓
5. 재테스트 (개선 효과 확인)
   ↓
6. 스트레스 테스트 (한계점 파악)
```

## 💡 핵심 포인트

1. **자동화**: k6 스크립트는 모든 API를 자동으로 테스트
2. **실제 계정**: config.js에 DB의 실제 사용자 정보 입력 필요
3. **데이터 안전**: update 설정은 데이터를 삭제하지 않음
4. **단계적 접근**: 스모크 → 부하 → 개선 → 재테스트 → 스트레스
5. **성능 목표**: 명확한 임계값 설정 (P95 < 500ms 등)
